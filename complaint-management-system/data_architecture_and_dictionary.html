Complaint Management System (CMS) Data Architecture & Data Dictionary



Executive Summary


The Complaint Management System (CMS) serves as a critical customer retention and operational risk-mitigation tool. This document details the end-to-end data architecture and logical relational design that underpins the system’s workflow. By formalizing core data models, SLA metrics pipelines, audit-trail compliance schemas, and integrations with Core Banking and Customer Relationship Management (CRM) databases, this schema ensures secure, high-performance, and verifiable operation.



1. Conceptual Data Model


The conceptual data model represents the high-level business concepts, workflows, and logical entities in the CMS. Each entity performs a distinct role in tracking, validating, and resolving customer complaints.


Business Entities & Descriptions


Entity Name Conceptual Purpose
Customer Represents the core consumer or business client lodging the grievance. Holds credentials, segments, risk scores, and account links.
Complaint The central case entity containing the core ticket number, creation metadata, current lifecycle state, and core descriptions.
Complaint Category Classification hierarchy (e.g., Financial, ATM, Internet Banking) used for routing and grouping.
Complaint Priority System urgency levels (Critical, High, Medium, Low) set by CMD to drive SLA schedules.
User System users representing internal staff (CMD Screeners, Work Unit resolvers, Auditors, Committee Members).
Role Security authorizations (e.g., ROLE_CMD_OFFICER, ROLE_AUDIT_TEAM) controlling feature and task access.
Department Corporate organizational units (e.g., Bole Branch, Card Services) mapped for Work Unit assignments.
CMD Screening Historical screening details containing triage notes, routing decisions, and initial priority assignments.
Investigation Audit trail of compliance investigations, complete with compliance findings and evidentiary files.
Chief Committee Review Review records of committee decisions regarding contested or high-impact compliance cases.
Resolution Work Unit resolution log detailing technical actions taken, resolver details, and dates.
Customer Feedback Captures satisfaction or dissatisfaction and comments from customers after notification.
SLA Configuration Predefined deadlines mapped by Category and Priority (total allowed minutes, threshold alarms).
Complaint SLA Metrics High-level compliance health tracking for process instance lifecycles (ON_TIME, OVERDUE, APPROACHING).
Task Time Tracking Granular temporal logging at the user-task level to measure individual and team operational bottleneck periods.
Audit Log Chronological record of system operations, previous vs. new values, actors, and remarks.
Attachment Links uploaded files (evidence, recordings, audit files, committee briefs) to their parent contexts.
Notification Tracks outgoing client communications via SMS and Email, indicating execution statuses.

Cardinality and Relationships


  • Customer (1) → (Many) Complaints**: A customer can file multiple complaints over time; each complaint relates to exactly one customer profile.
  • Complaint (1) → (Many) Audit Logs**: A single complaint case will trigger multiple audit trail events (e.g., Case Registered, Screened, Escalated, Resolved, Closed).
  • Department (1) → (Many) Users**: Internal bank staff members are assigned to one bank branch or department.
  • Role (1) → (Many) Users**: Users are assigned a primary system authorization role.
  • Complaint (1) → (Many) Attachments**: A complaint can contain multiple attachments at different workflow stages (Evidence from Customer, Voice Call recording, Auditor's Report, Committee Brief).
  • Complaint (1) → (Many) Notifications**: A single complaint triggers multiple customer notifications (Acknowledge SMS, Acknowledge Email, Resolution SMS, Feedback requests).
  • Complaint (1) → (1) SLA Metrics**: Every complaint has exactly one active process SLA tracking record.

6. SLA Data Structure


SLA management uses a configuration table and two runtime metrics tables to monitor resolution compliance.

  - sla_config_id (PK)
  - category_id (FK)
  - priority_id (FK)
  - total_sla_duration_minutes
  - escalation_threshold_percent
        |
        +-- (Used to validate & alert on)
        |
        v
[complaint_sla_metrics]
  - sla_metric_id (PK)
  - complaint_id (FK)
  - start_time
  - end_time
  - actual_duration_minutes
  - sla_status (ON_TIME, APPROACHING, OVERDUE)

1. sla_configurations: Defines the target SLA durations and warning thresholds for each category and priority combination.

2. complaint_sla_metrics: Tracks overall resolution compliance for each complaint.

3. task_time_trackings: Records fine-grained timing for individual tasks within the workflow, highlighting where delays occur.



7. Security and User Management


The security schema implements Role-Based Access Control (RBAC) to ensure that users can access and edit only those cases aligned with their authorizations.

  • Roles**: Contains the primary permission controls mapped to system endpoints and frontend layouts.
  • Departments**: Maps team members to structural groups, supporting task routing for Work Units.

9. Recommendations and Best Practices


1. Implement DB Partitioning on Audit Tables: The audit_logs and task_time_trackings tables grow rapidly. Partitioning them by calendar month or year improves query performance and simplifies archiving.

2. Define Indexes on Foreign Keys: Add indexes to foreign keys (complaint_id, customer_id, process_instance_id) to speed up dashboard queries and joint operations under high workloads.

3. Enforce Strict base64 Sanitation: File uploads are converted to base64 strings during frontend uploads. The backend must enforce file size limits and scan files before saving them to disk.

4. Use Asynchronous SLA Calculations: Calculate SLA deadlines asynchronously inside Spring Boot, or configure cron processes for status checks (like changing status from ON_TIME to APPROACHING). This keeps active process execution fast and lightweight.
